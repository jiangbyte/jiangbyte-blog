## 先说结论

Linux 默认认为 `1-1023` 是特权端口（端口 `0` 是“由内核分配临时端口”的特殊值），普通用户绑定 `80`、`89` 时会得到：

```text
PermissionError: [Errno 13] Permission denied
```

这次把内核参数 `net.ipv4.ip_unprivileged_port_start` 从默认的 `1024` 改为 `80`：

```bash
sudo sysctl -w net.ipv4.ip_unprivileged_port_start=80
```

改动后，普通用户可以显式绑定 `80-65535`；其中 `1-79` 仍是特权端口。对本次需求而言，`80` 正好是能够同时覆盖 80 和 89 的最低阈值。

## 这个参数不是端口白名单

参数名里的 `port_start` 表示“非特权端口从哪个端口开始”，而不是单独指定某个端口：

| 设置值 | 普通用户可绑定范围 | 仍属特权范围 |
| --- | --- | --- |
| `1024` | `1024-65535` | `1-1023` |
| `89` | `89-65535` | `1-88` |
| `80` | `80-65535` | `1-79` |
| `0` | `1-65535` | 无（端口 `0` 仍保留特殊语义） |

因此：

- 要同时让普通用户绑定 80 和 89，应设为 `80`。
- 如果设为 `89`，普通用户仍然不能绑定 80。
- 如果没有特殊需求，不要直接设为 `0`，否则 1、22、53 等低端口也会一并放开。

这是一项按网络命名空间生效的系统级策略。修改会同时影响该命名空间内之后创建的普通进程，不需要逐个给程序授权。

## 临时修改与持久化

### 先看当前值

```bash
sysctl net.ipv4.ip_unprivileged_port_start
cat /proc/sys/net/ipv4/ip_unprivileged_port_start
```

Debian 默认通常输出：

```text
net.ipv4.ip_unprivileged_port_start = 1024
```

如果提示 `sysctl: command not found`，先安装 `procps`：

```bash
sudo apt update
sudo apt install procps
```

### 立即生效

```bash
sudo sysctl -w net.ipv4.ip_unprivileged_port_start=80
```

输出应为：

```text
net.ipv4.ip_unprivileged_port_start = 80
```

### 写入持久化配置

建议使用独立的 `sysctl.d` 文件，避免直接改大而全的 `/etc/sysctl.conf`：

```bash
sudo tee /etc/sysctl.d/99-unprivileged-ports.conf >/dev/null <<'EOF'
# Allow unprivileged users to bind TCP/UDP ports from 80 upward.
net.ipv4.ip_unprivileged_port_start = 80
EOF
```

重新读取这个文件：

```bash
sudo sysctl -p /etc/sysctl.d/99-unprivileged-ports.conf
```

在正常启动 systemd 的 Debian 主机上，`systemd-sysctl` 会自动处理 `/etc/sysctl.d/*.conf`。如果系统没有使用 systemd，需要在初始化脚本中显式执行 `sysctl --system`，否则文件写入成功也不代表重启后一定生效。

重启前可以先确认配置已经写入：

```bash
cat /etc/sysctl.d/99-unprivileged-ports.conf
cat /proc/sys/net/ipv4/ip_unprivileged_port_start
```

## 用普通用户实际验证

仅查看 `sysctl` 的返回值还不够。切换或使用普通用户账户，直接尝试绑定端口：

```bash
python3 - <<'PY'
import socket

for port in (80, 89):
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as sock:
        sock.bind(("127.0.0.1", port))
        print(f"bound {port}")
PY
```

本次在 Debian 13、普通用户 UID 1000 下得到的实际结果：

```text
bound 80
bound 89
```

也可以直接启动一个普通用户服务：

```bash
python3 -m http.server 80 --bind 127.0.0.1
```

然后在另一个终端访问：

```bash
curl -I http://127.0.0.1/
```

再验证边界，普通用户绑定 79 应仍然失败：

```bash
python3 - <<'PY'
import socket

with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as sock:
    sock.bind(("127.0.0.1", 79))
PY
```

预期得到：

```text
PermissionError: [Errno 13] Permission denied
```

这说明改动只是把“特权范围”从 `1-1023` 缩小到了 `1-79`，并没有把所有权限检查都关闭。

## 容器里为什么可能没有生效

端口起始值是网络命名空间的一部分。宿主机执行了：

```bash
sudo sysctl -w net.ipv4.ip_unprivileged_port_start=80
```

已经存在或之后单独创建的网络命名空间不会自动继承这项修改。Docker 容器需要显式传入：

```bash
docker run --rm \
  --sysctl net.ipv4.ip_unprivileged_port_start=80 \
  your-image
```

Docker Compose 可以写成：

```yaml
services:
  app:
    image: your-image
    sysctls:
      net.ipv4.ip_unprivileged_port_start: "80"
```

如果容器使用 `network_mode: host`，它共享宿主机网络命名空间，此时应修改宿主机参数，而不是只修改容器参数。Kubernetes 则需要在 Pod 的 `securityContext.sysctls` 中声明，并确认集群的安全策略允许该键。

容器内写入 `/etc/sysctl.d/` 只修改容器文件系统，不会自动修改运行中的内核参数；容器是否在启动时读取这些文件，也取决于镜像和 init 进程。

## 80 外还有其他限制

降低端口阈值只解决了内核的端口权限检查，以下问题仍然可能出现：

- `EADDRINUSE`：端口已被 Nginx、Docker 或其他进程占用，需要先排查监听者。
- `EACCES`：进程仍受 AppArmor、SELinux、容器安全策略或系统调用过滤限制。
- 防火墙拦截：本地绑定成功不代表外部网络能访问。
- IPv4/IPv6 差异：验证时同时检查应用实际使用的地址族和监听地址。

查看监听状态：

```bash
ss -ltnp
ss -lunp
```

普通用户通常看不到其他用户进程名；需要完整进程信息时可使用：

```bash
sudo ss -ltnp
```

## 安全取舍

把阈值设为 80 后，任何能够登录这台机器并创建进程的用户，都可以尝试绑定 80 及以上的任意端口，包括 443、8080 等。它扩大的是所有本地非特权进程的绑定范围，并不是只针对某一个应用授权。

对单人开发机、受控的测试环境，这通常足够简单。对多用户共享主机或公网生产环境，可以优先考虑进程级方案：

```ini
[Service]
User=app
ExecStart=/usr/local/bin/app
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
NoNewPrivileges=yes
```

这样可以只给指定 systemd 服务授予绑定低端口的能力，不必改变整台机器的全局阈值。还可以配合非特权端口加反向代理，让 Nginx 等入口服务占住 80/443，业务进程只监听 8000、8080 等高端口。

## 回滚

如果不再需要这项修改，删除持久化文件并恢复默认阈值：

```bash
sudo rm /etc/sysctl.d/99-unprivileged-ports.conf
sudo sysctl -w net.ipv4.ip_unprivileged_port_start=1024
```

已经由普通用户启动、且仍占用 80 或 89 的进程不会被重启；必要时先停止这些服务，再恢复端口策略。
